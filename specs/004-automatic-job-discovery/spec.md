# Feature Specification: 자동 통합 채용공고 탐색

**Feature Branch**: codex/initial-implementation
**Created**: 2026-08-08
**Status**: Draft
**Input**: "구직자가 여러 채용 서비스에 흩어진 공고를 한 곳에서 자동으로 탐색하고 관리할 수 있는 제품 구조로 바로잡는다."
**Supersedes**: 001-job-posting-hub와 002-service-readiness의 수동 URL 등록 우선 가정. 기존 문서는 이력으로 보존하며 충돌 시 이 문서를 따른다.

## Scope

### In Scope

- 이용 허가가 확인된 복수 출처의 채용공고를 주기적으로 수집한다.
- 출처별 공고를 공통 구조로 정규화하고 중복 후보를 제안하며, 사용자 확인을 거쳐 개인 화면에서 대표 공고로 묶는다.
- 로그인한 구직자가 직접 등록 없이 통합 피드에서 검색, 필터, 정렬, 상세 확인을 한다.
- 공고 저장, 제외, 지원 상태와 개인 메모 관리를 제공한다.
- 출처, 원문 링크, 최신 확인 시각과 데이터 상태를 명확히 표시한다.
- 자동 범위 밖 공고를 위한 수동 URL 등록은 보조 기능으로 유지한다.

### Out of Scope

- 접근 제한 우회 또는 이용 허가 없는 자동 수집
- 구직자나 기업이 이 서비스에 채용공고를 게시하는 기능
- 사용자를 대신한 실제 입사 지원서 제출
- 재배포 권한이 없는 원문 전체, 기업 리뷰, 연봉 정보의 복제
- 출처에 없는 내용을 확정 사실처럼 생성하는 기능
- 결제, 기업 계정, 광고, 익명 공개 탐색

## Clarifications

### Session 2026-08-08

- Q: 종료되거나 출처에서 삭제된 공고를 어떻게 보존할까요? → A: 개인 메모·지원 상태와 최소 식별정보·원문 링크만 보존한다.
- Q: 공개 베타의 복수 출처 기준은 무엇인가요? → A: 별도 허가·접근수단을 가진 제공자 2개와 활성 공고 총 100개 이상으로 한다.
- Q: 개인 저장·제외·지원 상태가 기본 피드 순위에 영향을 주나요? → A: 공통 결정적 피드에 개인 상태만 겹쳐 표시하고 행동 기반 추천은 하지 않는다.
- Q: 피드 페이지와 기본 정렬·결측값 규칙은 무엇인가요? → A: 30개 단위 더 보기, 게시일·수집시각 순, 확인된 필터값만 일치시킨다.
- Q: 모바일·접근성 합격 기준은 무엇인가요? → A: WCAG 2.2 AA, 360px 무가로스크롤, 44px 터치 대상으로 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 자동으로 모인 공고 둘러보기 (Priority: P1)

로그인한 구직자는 URL을 등록하지 않아도 여러 허용 출처의 최신 공고를 첫 화면에서 살펴본다.

**Why this priority**: 파편화된 공고를 한곳에서 보는 것이 핵심 가치이며, 이 흐름이 없으면 단순 북마크 도구에 머문다.

**Independent Test**: 공고를 등록한 적 없는 신규 계정으로 로그인해 둘 이상의 허용 출처에서 온 공고와 각 원문 링크를 확인할 수 있으면 검증된다.

**Acceptance Scenarios**:

1. **Given** 활성 공고가 수집되어 있고 신규 사용자가 로그인했을 때, **When** 기본 화면을 열면, **Then** 사전 입력 없이 최신 공고 목록이 표시된다.
2. **Given** 서로 다른 출처의 공고가 있을 때, **When** 목록을 보면, **Then** 각 공고의 출처와 원문 이동 수단이 표시된다.
3. **Given** 일부 출처 갱신이 실패했을 때, **When** 피드를 열면, **Then** 정상 출처와 이전 유효 공고는 계속 보이고 최신성 상태가 안내된다.

---

### User Story 2 - 원하는 조건으로 좁히기 (Priority: P2)

구직자는 키워드, 근무지, 직무, 경력, 고용 형태, 마감 상태, 출처를 조합해 원하는 공고를 찾는다.

**Why this priority**: 통합 후 늘어난 공고를 실제로 활용하려면 빠른 검색과 필터가 필요하다.

**Independent Test**: 알려진 속성의 시험 공고에서 검색, 필터, 정렬을 적용해 일치하는 공고만 나오고 조건을 초기화할 수 있으면 검증된다.

**Acceptance Scenarios**:

1. **Given** 다양한 공고가 있을 때, **When** 검색어와 필터를 적용하면, **Then** 모든 조건에 맞는 대표 공고만 표시된다.
2. **Given** 결과가 없을 때, **When** 결과 화면이 나타나면, **Then** 적용 조건, 결과 없음 안내, 조건 해제 수단이 함께 보인다.
3. **Given** 여러 결과가 있을 때, **When** 최신순 또는 마감 임박순을 선택하면, **Then** 선택 기준에 따라 순서가 바뀐다.

---

### User Story 3 - 관심 공고와 지원 진행 관리 (Priority: P3)

구직자는 공고를 저장하거나 제외하고 지원 예정, 지원 완료, 전형 진행, 종료 상태와 개인 메모를 관리한다.

**Why this priority**: 탐색을 실제 취업 준비 행동으로 연결하고 반복 사용 가치를 만든다.

**Independent Test**: 공고 저장 후 상태와 메모를 변경하고 다시 로그인하거나 출처가 갱신된 뒤에도 개인 상태가 유지되면 검증된다.

**Acceptance Scenarios**:

1. **Given** 공고 상세를 보고 있을 때, **When** 저장을 선택하면, **Then** 개인 저장 목록에 나타난다.
2. **Given** 저장 공고가 있을 때, **When** 상태나 메모를 바꾸면, **Then** 해당 사용자에게만 보이고 이후에도 유지된다.
3. **Given** 저장 공고가 종료 또는 제거되었을 때, **When** 개인 목록을 열면, **Then** 종료 상태가 표시되고 개인 상태와 메모는 보존된다.

---

### User Story 4 - 중복과 출처 확인하기 (Priority: P4)

구직자는 같은 채용으로 보이는 공고를 중복 후보로 확인하고, 사용자 확인을 거쳐 개인 화면에서 하나의 대표 공고로 묶거나 다시 분리한다.

**Why this priority**: 중복 노출과 불명확한 출처는 통합 서비스의 신뢰를 훼손한다.

**Independent Test**: 동일 채용의 복수 출처 시험 데이터가 중복 후보로 제시되고, 사용자가 병합·분리한 뒤에도 모든 원문 링크와 개인 상태가 보존되면 검증된다.

**Acceptance Scenarios**:

1. **Given** 동일 채용으로 보이는 공고가 여러 출처에 있을 때, **When** 중복 후보가 제시되면, **Then** 사용자는 병합 또는 별개 유지 여부를 선택할 수 있다.
2. **Given** 출처별 마감일이나 조건이 다를 때, **When** 상세를 열면, **Then** 값별 출처를 구분해 확인할 수 있다.
3. **Given** 사용자가 병합한 공고가 있을 때, **When** 병합 취소를 선택하면, **Then** 원문 링크와 개인 상태를 잃지 않고 다시 분리된다.

---

### User Story 5 - 자동 범위 밖 공고 보완하기 (Priority: P5)

구직자는 자동 피드에 없는 공고를 선택적으로 URL로 추가해 개인 목록에서 관리한다.

**Why this priority**: 자동 수집 누락을 보완하지만 핵심 탐색보다 앞서는 흐름은 아니다.

**Independent Test**: 보조 경로에서 URL을 추가하고 자동 공고와 구분된 출처 및 개인 상태를 관리할 수 있으면 검증된다.

**Acceptance Scenarios**:

1. **Given** 피드에 없는 공고 URL이 있을 때, **When** 보조 등록하면, **Then** 확인된 값과 사용자 입력이 구분되어 개인 목록에 추가된다.
2. **Given** URL에서 정보를 읽을 수 없을 때, **When** 등록을 계속하면, **Then** 최소 정보를 직접 보완하거나 취소할 수 있다.
3. **Given** 수동 공고가 이후 자동 공고와 일치할 때, **When** 중복이 확인되면, **Then** 개인 상태를 잃지 않고 대표 공고에 연결된다.

### Edge Cases

- 일부 또는 전체 출처가 중단되거나 응답 제한에 도달한다.
- 출처 이용 허가나 제공 조건이 변경 또는 철회된다.
- 외부 식별자나 URL은 달라졌지만 실제 채용은 같다.
- 회사명은 같지만 법인, 지역, 직무가 다른 공고가 유사하다.
- 출처마다 마감일, 경력, 근무지 값이 다르다.
- 상시 채용, 조기 마감, 재게시처럼 마감 상태가 불명확하다.
- 수집 도중 일부 범위만 성공하고 중단된다.
- 종료 공고를 별도로 반환하지 않는 출처에서 한 번의 누락만 발생한 경우
- 저장 공고가 삭제, 비공개, 종료되거나 출처에서 사라진다.
- 최초 수집 전이거나 검색 결과가 없어 피드가 비어 있다.
- 비정상적으로 긴 값이나 표시를 방해하는 문자가 포함된다.
- 같은 개인 상태를 여러 화면에서 동시에 변경한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 이용 허가와 접근 조건이 확인된 출처만 자동 수집 대상으로 활성화해야 한다.
- **FR-002**: 공개 베타 전 별도 이용허가, 접근수단, 출처 식별자를 가진 데이터 제공자 둘 이상과 활성 공고 총 100개 이상을 확보해야 한다. 같은 원천 데이터를 재유통하는 채널은 별도 제공자로 세지 않는다.
- **FR-002a**: 출시 후 독립 제공자가 둘 미만 또는 활성 공고가 100개 미만으로 감소하면 기존 피드와 개인 기록은 읽을 수 있게 유지하되 복수 출처 서비스라는 표시를 중단하고 운영 경고를 제공해야 한다.
- **FR-003**: 출처가 허용한 접근 범위와 빈도를 우선 준수하면서 신규·변경 공고는 목표 6시간 이내에 반영해야 한다. 종료 여부는 완전 수집에서 연속 2회 누락되거나 출처가 명시적으로 종료를 알린 경우에 확정하며 목표 24시간 이내에 공개 피드에서 제외해야 한다.
- **FR-004**: 신규 사용자는 직접 등록하지 않고 로그인 후 기본 화면에서 자동 공고를 탐색할 수 있어야 한다.
- **FR-005**: 공고를 회사명, 제목, 근무지, 직무, 경력, 고용 형태, 게시일, 마감일, 원문 URL, 출처 상태의 공통 구조로 정리해야 한다.
- **FR-006**: 시스템은 교차 출처 중복을 후보로 제안해야 하며, 사용자 확인 없이 공고를 비가역적으로 병합해서는 안 된다. 병합 후에도 모든 출처 참조와 원문 링크를 보존해야 한다.
- **FR-007**: 사용자는 제안된 중복을 병합하지 않고 별개로 유지하거나, 이전 병합을 되돌릴 수 있어야 하며 이 과정에서 정보나 개인 상태를 잃어서는 안 된다.
- **FR-008**: 키워드 검색과 근무지, 직무, 경력, 고용 형태, 마감 상태, 출처 필터를 제공해야 한다.
- **FR-009**: 기본 정렬은 확인 가능한 게시일 내림차순, 마지막 수집 시각 내림차순, 대표 공고 식별자 순으로 결정하며 최신순, 마감 임박순과 모든 조건 초기화를 제공해야 한다.
- **FR-009a**: 결과는 30개 단위의 명시적 더 보기로 탐색하고, 필터와 정렬은 주소에 유지하며 상세에서 돌아왔을 때 목록 위치와 초점이 복원되어야 한다.
- **FR-009b**: 활성 필터는 출처에서 확인된 값만 일치시켜야 하며 해당 값이 없는 공고는 일치 결과에서 제외하고 정보 없음 건수를 별도로 알려야 한다.
- **FR-010**: 목록과 상세에 출처, 원문 이동 수단, 마지막 확인 시각, 활성, 종료, 최신성 불확실 상태를 표시해야 한다.
- **FR-011**: 사용자는 저장, 제외, 제외 취소, 지원 상태, 개인 메모를 관리할 수 있어야 한다.
- **FR-011a**: 기본 피드의 공고 순서는 모든 사용자에게 동일한 결정 규칙을 따라야 한다. 저장·지원 상태는 배지로 표시하고 제외 공고는 기본적으로 숨기되 별도 보기에서 복원할 수 있어야 하며, 행동 기반 개인 추천은 이 기능 범위에 포함하지 않는다.
- **FR-012**: 개인 상태는 공용 공고와 분리되며 해당 사용자만 조회, 변경할 수 있어야 한다.
- **FR-013**: 공고 종료·삭제 또는 출처 중단 후에는 공개 피드에서 해당 공고를 제외하고, 개인 메모·지원 상태와 출처가 허용한 최소 식별정보·원문 링크만 보존해야 한다.
- **FR-014**: 한 출처의 실패가 다른 출처 탐색과 개인 데이터 사용을 막아서는 안 된다.
- **FR-015**: 준비 중, 결과 없음, 부분 최신성 저하, 전체 갱신 실패를 구분해 다음 행동을 안내해야 한다.
- **FR-016**: 수동 URL 등록은 시각적, 동선상 보조 기능이어야 하며 첫 사용 완료 조건이어서는 안 된다.
- **FR-017**: 수동 등록의 출처 확인 값, 시스템 정리 값, 사용자 입력을 구분해야 한다.
- **FR-018**: 사용자는 저장, 제외, 지원 상태, 메모를 내보내고 복원할 수 있어야 한다.
- **FR-019**: 사용자를 대신해 실제 지원을 제출하거나 출처 접근 제한을 우회해서는 안 된다.
- **FR-020**: 운영자는 출처별 활성 여부, 마지막 성공, 실패, 수집 건수, 오류 요약을 확인하고 출처를 중단할 수 있어야 한다.
- **FR-021**: 시스템은 출처별 지정 귀속 문구, 링크, 표시 위치를 준수해야 하며 병합된 공고에서도 각 출처의 귀속 표시를 누락해서는 안 된다.

### Source & Data Trust Requirements

- **DT-001**: 모든 자동 공고는 출처 식별자, 출처 내 식별자, 원문 URL, 최초 및 마지막 확인 시각을 가져야 한다.
- **DT-002**: 출처 사실, 정규화 값, 시스템 추정, 사용자 입력은 저장과 표시에서 구분되어야 한다.
- **DT-003**: 출처 값이 충돌하면 근거 없이 하나를 확정하지 말고 출처별 값과 확인 시각을 보존해야 한다.
- **DT-004**: 출처가 허용한 범위와 빈도를 따르며 로그인 우회, 차단 회피, 비공개 접근을 사용해서는 안 된다.
- **DT-005**: 재배포 권한이 없으면 탐색에 필요한 최소 정보와 원문 링크만 제공해야 한다.
- **DT-006**: 허가 철회 시 신규 수집과 공개 표시를 중단하고, 공유 공고 필드는 출처가 허용한 범위와 기간에 따라 삭제해야 한다. 허용 범위가 불명확하면 개인 기록과 최소 식별정보·원문 링크 외의 장기 보존을 하지 않는다.
- **DT-007**: 중복 후보의 판단 근거와 연결 출처를 추적하고, 사용자 확인 결과와 병합·분리 이력을 보존하며 잘못된 병합을 되돌릴 수 있어야 한다.
- **DT-008**: 출처 장애나 오래된 데이터를 숨기지 말고 최신성 한계를 표시해야 한다.

### User Control & Recovery Requirements

- **UR-001**: 사용자는 저장, 제외, 지원 상태, 메모를 언제든 수정, 삭제할 수 있어야 한다.
- **UR-002**: 제외 목록을 확인하고 다시 탐색 대상으로 복원할 수 있어야 한다.
- **UR-003**: 자동 갱신이나 병합이 개인 상태를 조용히 덮어쓰거나 삭제해서는 안 된다.
- **UR-004**: 잘못 병합된 공고를 분리해도 개인 상태를 복구할 수 있어야 한다.
- **UR-005**: 사용자는 잘못된 정보, 중복, 원문 문제를 운영자 검토 대상으로 표시할 수 있어야 한다.
- **UR-006**: 내보낸 개인 데이터는 중복 생성 없이 복원할 수 있어야 한다.
- **UR-007**: 실패한 변경을 성공처럼 표시하지 말고 재시도 또는 취소를 안내해야 한다.

### Key Entities *(include if feature involves data)*

- **Source Provider**: 외부 출처의 허용 상태, 접근 조건, 갱신 주기, 최근 성공 및 실패 상태.
- **Source Posting**: 출처의 개별 공고와 외부 식별자, 원문 URL, 출처 사실, 확인 시각, 활성 상태.
- **Canonical Job**: 동일 채용으로 확인된 출처 공고를 묶는 대표 공고와 공통 탐색 속성.
- **Collection Run**: 한 차례 갱신의 범위, 시각, 발견, 변경, 종료 건수, 오류 요약.
- **Duplicate Decision**: 병합 및 분리 판단의 근거, 확신 수준, 변경 이력.
- **Personal Job State**: 사용자별 저장, 제외, 지원 상태, 메모, 변경 시각.
- **Manual Posting**: 보조 등록 URL, 확인 값, 사용자 입력, 대표 공고 연결 여부.
- **Source Issue Report**: 잘못된 정보나 중복에 대한 사용자 신고와 처리 상태.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 공개 전 시험에서 신규 사용자가 수동 등록 없이 독립 제공자 둘 이상의 활성 공고 총 100개 이상을 첫 화면에서 탐색할 수 있다.
- **SC-002**: 정상 출처의 대상 신규 및 변경 공고 95% 이상이 확인 후 6시간 안에 피드에 반영된다.
- **SC-003**: 대표 공고 1,000개 이상의 시험에서 검색, 필터, 정렬 결과 95%가 동작 후 2초 안에 표시된다.
- **SC-004**: 확정 중복 시험 집합 100%가 후보로 제시되고, 사용자의 병합·분리 선택 후 모든 원문 링크와 개인 상태가 보존된다.
- **SC-005**: 자동 공고 100%에서 출처별 지정 귀속 표시, 원문 이동 수단, 마지막 확인 시각을 확인할 수 있다.
- **SC-006**: 한 출처가 24시간 실패해도 다른 출처 탐색이 유지되고 개인 상태와 메모 손실은 0건이다.
- **SC-007**: 대표 사용자 시험 참여자 90% 이상이 설명 없이 2분 안에 관심 공고를 찾아 저장하며 수동 등록을 요구받지 않는다.
- **SC-008**: 개인 데이터 내보내기 및 복원 시험에서 유효 데이터 100%가 중복 없이 복구된다.
- **SC-009**: 종료 및 제거 공고 회귀 시험에서 개인 상태와 메모 손실은 0건이고, 허용되지 않은 공유 공고 필드의 장기 보존은 0건이다.
- **SC-010**: 허가 없는 접근, 접근 제한 우회, 사용자 대신 실제 지원 제출 사례는 출시 점검에서 0건이다.
- **SC-011**: 핵심 탐색·필터·저장 여정은 WCAG 2.2 AA를 충족하고 키보드만으로 완료 가능하며, 자동 접근성 검사에서 심각 또는 치명 오류가 0건이어야 한다.
- **SC-012**: 360 CSS 픽셀 너비에서 핵심 화면에 가로 스크롤이 없고 주요 터치 대상은 최소 44×44 CSS 픽셀이어야 한다.
- **SC-013**: 종료 상태를 직접 제공하지 않는 출처의 완전 수집 시험에서 한 번 누락된 공고는 활성으로 유지되고 연속 2회 누락된 공고의 95% 이상이 24시간 안에 공개 피드에서 제외된다.

## Assumptions

- 초기 사용자는 Google 계정으로 로그인한 개인 구직자이며 익명 공개 탐색은 후속 범위다.
- 사람인, 잡코리아, 잡플래닛 등은 후보 출처이며 실제 활성화는 허용된 접근 방식과 표시 조건이 확보된 경우에만 가능하다.
- 공개 베타에는 별도 허가와 접근수단을 가진 제공자 둘 이상과 활성 공고 총 100개 이상이 필요하며, 허용된 기업 채용 피드나 공공 채용 데이터도 포함될 수 있다.
- 원문이 최종 사실의 기준이며 정규화 정보는 탐색 편의를 위한 보조 표현이다.
- 교차 출처 중복은 후보로만 제안하고 사용자의 명시적 확인 후 개인 화면에서 병합하며 언제든 분리할 수 있다.
- 기존 수동 공고와 개인 상태는 자동 피드 도입 후에도 유지한다.

## Dependencies & Constraints

- 각 출처의 이용 약관, 접근 허가, 갱신 제한, 출처 표시 및 보관 조건
- 최소 두 출처에 대한 합법적이고 안정적인 자동 접근 수단
- 기존 로그인, 사용자별 접근 제어, 내보내기 및 복원 기능과의 호환성
- 출처별 필드 품질 차이로 모든 공고의 모든 필터 속성을 보장할 수 없음
- 외부 장애와 정책 변경을 통제할 수 없으므로 부분 실패와 중단을 정상 운영 상태로 처리해야 함
- 기존 001부터 003 산출물 중 이 문서와 충돌하지 않는 인증, 개인정보, 운영 안전 요구는 계속 유효함
