# Feature Specification: 개인용 통합 채용공고 허브

**Feature Branch**: `[002-job-posting-hub]`

**Created**: 2026-08-06

**Status**: Draft

**Input**: 여러 채용 플랫폼과 기업 채용 페이지에서 발견한 공고를 한곳에 모아 비교하고, 중복을 정리하며, 관심 및 지원 상태를 개인적으로 관리하는 웹 도구

## Clarifications

### Session 2026-08-06

- Q: MVP에서 자동 추출할 채용정보 출처의 범위는? → A: 사전 승인을 받고 자격 증명을 갖춘 사람인·잡코리아 공식 API만 사용하며, 승인 전이거나 다른 출처는 URL과 수동 입력으로 저장한다.
- Q: 개인 데이터는 어디에 저장하고 어떻게 여러 기기에서 이용할 것인가? → A: Google SSO로 개인 계정에 로그인하고 여러 기기에서 자동 동기화한다.
- Q: 채용공고 본문을 어느 범위까지 저장할 것인가? → A: 비교용 구조화 항목과 짧은 요약만 저장하고 전체 본문은 원문에서 확인한다.
- Q: 여러 기기에서 같은 데이터를 동시에 수정할 때 충돌을 어떻게 처리할 것인가? → A: 가장 최근 변경을 적용하고 이전 값은 변경 이력에서 복구할 수 있게 한다.
- Q: 저장된 공고의 최신 상태를 언제 다시 확인할 것인가? → A: 사람인·잡코리아 공고의 상세 화면을 열 때 자동으로 다시 확인한다.

## Scope *(mandatory)*

### In Scope

- 사용자가 발견한 채용공고 원문 URL 등록
- 승인·설정된 사람인·잡코리아 공식 API를 통한 핵심 정보 조회와 사용자 검토
- 비교에 필요한 구조화 항목과 짧은 요약의 저장
- 잡플래닛을 포함한 다른 출처의 URL 보관과 수동 입력
- 추출할 수 없거나 잘못된 정보의 수동 입력 및 수정
- 서로 다른 출처의 공고를 공통 항목으로 정리한 통합 목록
- 검색, 필터, 정렬을 통한 후보 탐색
- 동일 URL 차단과 유사 공고 후보 제안
- 사용자가 확정하는 중복 공고 묶기와 분리
- 관심 여부, 지원 단계, 메모, 다음 행동 일정 관리
- 마감 상태 및 원문 확인 상태 표시
- 사람인·잡코리아 공고 상세 화면 진입 시 최신 상태 자동 확인
- 사용자 데이터 내보내기와 복원
- Google SSO를 이용한 개인 계정 로그인
- 동일 계정으로 로그인한 여러 기기 간 자동 동기화

### Out of Scope

- 채용 사이트 전체를 자동으로 순회하는 대규모 또는 주기적 수집
- 잡플래닛을 포함해 MVP 지원 대상으로 지정되지 않은 출처의 자동 추출
- 로그인, 접근 제한 또는 기술적 차단을 우회하는 정보 수집
- 채용공고 전체 본문의 복제·보관 또는 원문을 대신하는 재게시
- 기업 리뷰, 연봉, 면접 후기 원문의 복제 또는 재배포
- 사용자 간 데이터 공유, 협업 및 관리자 기능
- 이력서 작성, 입사지원서 자동 제출 및 채용 플랫폼을 대신하는 지원 기능
- 근거 없이 하나의 숫자로 표현하는 AI 적합도 점수
- 모바일 전용 애플리케이션
- 네트워크 연결이 없는 상태에서 수정사항을 대기열에 저장하거나 자동 재전송하는 오프라인 편집
- 공개 서비스 운영에 필요한 결제·운영자·공개 게시 기능

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 발견한 공고 통합 저장 (Priority: P1)

구직자는 여러 사이트에서 발견한 공고의 URL을 등록하고, 확인된 핵심 정보를 검토한 뒤 하나의 목록에 저장한다.

**Why this priority**: 흩어진 정보를 한곳에 모으는 행위가 제품의 가장 작은 독립 가치이며 이후 모든 기능의 기반이다.

**Independent Test**: 승인된 공식 API fixture를 사용하는 사람인·잡코리아 URL과 그 밖의 출처 또는 접근할 수 없는 URL을 각각 등록해 API 확인, 사용자 수정, URL 보관 및 수동 등록 경로를 검증할 수 있다. 커넥터 승인이나 자격 증명이 없으면 네트워크 호출 없이 수동 등록으로 전환되어야 한다.

**Acceptance Scenarios**:

1. **Given** 공식 API 사용이 승인·설정된 사람인 또는 잡코리아 공고 URL, **When** 사용자가 등록하면, **Then** 공식 API에서 확인 가능한 핵심 정보와 출처·원문·확인 시각이 검토 가능한 상태로 표시된다.
2. **Given** 일부 항목을 확인할 수 없는 공고, **When** 사용자가 값을 보완하고 저장하면, **Then** 확인된 값과 사용자 입력값이 구분되어 보존된다.
3. **Given** 잡플래닛 등 자동 추출 대상이 아니거나 접근이 제한된 URL, **When** 등록을 시도하면, **Then** URL이 보관되고 대상 외 출처 또는 실패 이유와 원문 이동 및 수동 입력 경로가 제공된다.
4. **Given** 이미 저장된 동일 URL, **When** 다시 등록하면, **Then** 새 항목을 만들기 전에 기존 공고가 안내된다.

### User Story 2 - 조건에 맞는 공고 탐색 (Priority: P1)

구직자는 여러 출처의 공고를 공통 항목으로 비교하고 원하는 조건으로 후보를 빠르게 좁힌다.

**Why this priority**: 통합 저장만으로는 여러 사이트를 반복 탐색하는 부담을 충분히 줄일 수 없기 때문이다.

**Independent Test**: 서로 다른 조건의 공고 100개에서 키워드·필터·정렬을 조합해 목표 공고를 찾고 원문으로 이동할 수 있다.

**Acceptance Scenarios**:

1. **Given** 여러 회사와 직무의 공고 목록, **When** 회사명·공고 제목·직무 키워드를 검색하면, **Then** 일치하는 후보만 표시된다.
2. **Given** 서로 다른 지역·경력·고용형태·마감 상태의 공고, **When** 조건을 조합하면, **Then** 모든 조건을 만족하는 공고가 표시된다.
3. **Given** 필터와 정렬이 적용된 목록, **When** 사용자가 조건 초기화를 실행하면, **Then** 전체 기본 목록으로 돌아간다.
4. **Given** 값이 확인되지 않은 공고, **When** 목록과 상세를 보면, **Then** `정보 없음`, `해당 없음`, `확인 실패`가 서로 다르게 표시된다.

---

### User Story 3 - 유사·중복 공고 정리 (Priority: P1)

구직자는 여러 출처에 게시된 동일하거나 유사한 공고 후보를 확인하고 직접 묶거나 분리한다.

**Why this priority**: 중복 검토 시간을 줄이면서도 잘못된 자동 병합으로 후보를 잃지 않게 해야 한다.

**Independent Test**: 동일 URL, 명백히 동일한 타 출처 공고, 제목만 비슷한 별도 공고를 등록해 각 처리 결과를 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 회사·직무·근무지·기간이 유사한 공고, **When** 새 공고가 저장되면, **Then** 유사 판단 근거와 함께 중복 후보가 제시된다.
2. **Given** 중복 후보, **When** 사용자가 동일 공고로 확정하면, **Then** 하나의 묶음에서 모든 출처와 원문을 확인할 수 있다.
3. **Given** 묶인 공고, **When** 사용자가 판단을 취소하면, **Then** 공고가 다시 분리되고 사용자 기록은 보존된다.
4. **Given** 유사하지만 서로 다른 공고, **When** 사용자가 별개로 유지하면, **Then** 이후에도 자동으로 병합되지 않는다.

---

### User Story 4 - 지원 진행 상태 관리 (Priority: P1)

구직자는 관심 공고를 선별하고 지원부터 결과까지의 상태, 메모, 다음 행동을 기록한다.

**Why this priority**: 공고 탐색을 실제 지원 행동으로 이어주며 개인용 도구의 지속 사용 가치를 만든다.

**Independent Test**: 공고 하나를 검토 전부터 지원 완료와 최종 결과까지 이동하고 기록 보존 여부를 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 저장된 공고, **When** 사용자가 상태를 변경하면, **Then** 현재 상태와 변경 시각이 보존된다.
2. **Given** 상태·메모·일정이 있는 공고, **When** 원문이 종료되거나 중복 묶음이 변경되면, **Then** 사용자 기록이 유지된다.
3. **Given** 제외한 공고, **When** 기본 목록을 열면, **Then** 숨겨지며 제외 조건을 선택하면 다시 찾을 수 있다.
4. **Given** 잘못 변경한 상태, **When** 사용자가 올바른 상태로 다시 변경하면, **Then** 기록 손실 없이 수정된다.
5. **Given** 한 기기에서 공고나 지원 기록을 변경한 사용자, **When** 다른 기기에서 동일한 Google 계정으로 로그인하면, **Then** 동기화된 최신 기록을 확인할 수 있다.
6. **Given** 두 기기에서 같은 값을 서로 다르게 수정한 사용자, **When** 동기화가 완료되면, **Then** 가장 최근 변경이 현재값으로 표시되고 이전 값은 변경 이력에서 복구할 수 있다.

---

### User Story 5 - 마감과 원문 상태 확인 (Priority: P2)

구직자는 마감이 임박하거나 종료된 공고와 원문을 더 이상 확인할 수 없는 공고를 구분한다.

**Why this priority**: 지원 기회를 놓이는 일을 줄이지만 공고 저장·탐색·지원 관리 이후에도 추가할 수 있다.

**Independent Test**: 오늘 마감, 임박, 마감 경과, 상시채용, 마감 미정, 원문 확인 실패 사례를 각각 표시해 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 마감일이 알려진 공고, **When** 목록을 열면, **Then** 남은 기간 또는 마감 여부가 표시된다.
2. **Given** 상시채용과 마감일 미정 공고, **When** 목록을 열면, **Then** 두 상태가 서로 구분된다.
3. **Given** 원문이 삭제되거나 접근 불가능한 공고, **When** 상태를 확인하면, **Then** 마지막 성공 시각과 현재 확인 실패 상태가 표시되고 사용자 기록은 유지된다.
4. **Given** 저장된 사람인 또는 잡코리아 공고, **When** 사용자가 상세 화면을 열면, **Then** 저장된 내용이 즉시 표시되고 최신 상태 확인이 자동으로 시작된다.
5. **Given** 상세 화면에서 자동 확인 중인 공고, **When** 확인이 성공하거나 실패하면, **Then** 화면 이용을 막지 않고 갱신 결과 또는 실패 상태와 확인 시각이 표시된다.

### Edge Cases

- 로그인 또는 접근 권한이 필요한 원문 URL
- 공고가 삭제되거나 다른 주소로 이동해 전체 본문을 다시 확인할 수 없는 경우
- 같은 URL의 내용이 다른 채용공고로 교체된 경우
- 주요 내용이 이미지 또는 첨부파일에만 존재하는 경우
- 회사명 약칭·법인명·브랜드명·영문명이 서로 다른 중복 공고
- 제목은 같지만 직무·근무지·채용 인원이 다른 공고
- 제목은 다르지만 실제 모집 내용과 기간이 동일한 공고
- 여러 직무 또는 여러 지역을 한 페이지에서 동시에 모집하는 공고
- 채용 시 마감, 상시채용, 마감 연장 또는 마감일이 없는 공고
- 급여가 범위·협의·회사 내규 등으로 표현된 공고
- 공고 정보와 사용자가 수정한 값이 이후 서로 달라지는 경우
- 네트워크 연결 없이 저장을 시도한 경우 서버 현재값은 변경되지 않고 실패 안내와 재연결 후 재시도 경로가 제공되어야 하며, 오프라인 변경 대기열은 만들지 않는다.
- 묶인 출처 중 일부만 종료된 경우
- 상세 화면을 여는 동안 원문 확인이 느리거나 실패하는 경우
- 잘못된 중복 확정 또는 상태 변경을 사용자가 되돌리는 경우
- 내보내기 파일이 손상되었거나 현재 데이터와 충돌하는 경우

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 사용자는 원문 URL을 입력하여 공고 등록을 시작할 수 있어야 한다.
- **FR-002**: 시스템은 승인과 서버 자격 증명이 모두 확인된 경우에만 사람인·잡코리아 공식 API의 허용된 구조화 정보를 조회해 저장 전 검토 상태로 제시해야 하며, 그 외에는 네트워크 호출 없이 수동 등록으로 전환해야 한다.
- **FR-003**: 사용자는 제목, 회사명, 직무, 주요 업무, 자격요건, 우대사항, 경력, 학력, 고용형태, 근무지역, 급여, 역량 키워드, 게시일, 마감일을 입력하거나 수정할 수 있어야 한다.
- **FR-004**: 시스템은 동일 URL이 존재하면 새 공고 생성 전에 기존 공고를 안내해야 한다.
- **FR-005**: 사용자는 잡플래닛을 포함한 자동 추출 대상 외 출처 또는 정보 추출 실패 공고의 URL을 보관하고 내용을 수동으로 등록할 수 있어야 한다.
- **FR-006**: 사용자는 회사명·제목·직무 키워드로 공고를 검색할 수 있어야 한다.
- **FR-007**: 사용자는 지역, 경력, 고용형태, 사용자 상태, 출처, 마감 상태로 공고를 필터링할 수 있어야 한다.
- **FR-008**: 사용자는 등록일, 게시일, 마감 임박 순으로 공고를 정렬할 수 있어야 한다.
- **FR-009**: 목록은 제목, 회사명, 직무, 지역, 경력, 고용형태, 마감일, 출처, 사용자 상태를 비교 가능한 형태로 표시해야 한다.
- **FR-010**: 시스템은 확인 가능한 회사명, 제목, 직무, 근무지역, 게시 기간을 근거로 유사 공고 후보를 표시해야 한다.
- **FR-011**: 사용자는 중복 후보를 동일 공고로 묶거나 별개로 유지하고, 확정한 판단을 나중에 변경할 수 있어야 한다.
- **FR-012**: 중복 묶음은 포함된 모든 출처와 원문 URL을 유지해야 한다.
- **FR-013**: 사용자는 공고 상태를 `검토 전`, `관심`, `지원 예정`, `지원 완료`, `전형 진행`, `최종 합격`, `불합격`, `제외` 중 하나로 지정할 수 있어야 한다.
- **FR-014**: 사용자는 공고별 개인 메모와 다음 행동 일정을 작성·수정·삭제할 수 있어야 한다.
- **FR-015**: 시스템은 사용자 상태의 변경 내용과 변경 시각을 보존해야 한다.
- **FR-016**: 제외 공고는 기본 목록에서 숨겨지고 사용자가 조건을 선택하면 다시 표시되어야 한다.
- **FR-017**: 시스템은 마감 임박, 마감 경과, 상시채용, 마감일 미정 상태를 구분해야 한다.
- **FR-018**: 원문 종료·접근 실패 또는 중복 묶음 변경 이후에도 사용자 메모와 지원 활동을 보존해야 한다.
- **FR-019**: 사용자는 저장된 사용자 데이터 전체를 일반적으로 재사용 가능한 파일로 내보낼 수 있어야 한다.
- **FR-020**: 사용자는 유효한 내보내기 파일을 이용해 공고와 사용자 기록을 복원할 수 있어야 한다.
- **FR-021**: 복원 과정에서 손상되거나 호환되지 않는 데이터가 발견되면 기존 데이터를 변경하기 전에 오류와 영향 범위를 안내해야 한다.
- **FR-022**: 사용자는 Google SSO를 이용해 개인 계정에 로그인하고 로그아웃할 수 있어야 한다.
- **FR-023**: 로그인한 사용자는 자신의 공고, 메모, 일정 및 지원 기록에만 접근할 수 있어야 한다.
- **FR-024**: 동일 계정으로 로그인한 여러 기기는 사용자의 공고와 지원 기록을 자동으로 동기화해야 한다.
- **FR-025**: 시스템은 비교에 필요한 구조화 항목과 짧은 요약만 저장하고 채용공고 전체 본문을 복제·보관해서는 안 된다.
- **FR-026**: 사용자는 저장된 구조화 정보와 요약에서 원문 공고로 이동할 수 있어야 한다.
- **FR-027**: 여러 기기에서 같은 값이 충돌하면 시스템은 변경 시각이 가장 최근인 값을 현재값으로 적용해야 한다.
- **FR-028**: 시스템은 동기화 충돌로 교체된 이전 값, 변경 시각 및 변경 기기를 이력으로 보존해야 한다.
- **FR-029**: 사용자는 변경 이력의 이전 값을 현재값으로 복구할 수 있어야 한다.
- **FR-030**: 사용자가 저장된 사람인·잡코리아 공고의 상세 화면을 열면 시스템은 원문의 최신 상태 확인을 자동으로 시작해야 한다.
- **FR-031**: 상세 화면은 최신 상태 확인을 기다리지 않고 저장된 정보를 먼저 표시하고 확인 진행 상태를 알려야 한다.
- **FR-032**: 최신 상태 확인의 성공 또는 실패는 상세 화면 이용을 차단하지 않고 결과, 확인 시각 및 실패 이유를 표시해야 한다.
- **FR-033**: 네트워크 연결 없이 수정 저장을 시도하면 시스템은 서버 현재값을 변경된 것으로 표시해서는 안 되며, 저장 실패와 재연결 후 재시도 방법을 안내해야 한다.

### Source & Data Trust Requirements *(mandatory when external data is involved)*

- **DT-001**: 각 공고는 출처 이름, 원문 URL, 최초 등록 시각, 마지막 확인 시각을 보존해야 한다.
- **DT-002**: 시스템은 원문에서 확인한 값, 정규화·추론한 값, 사용자 입력값, 정보 없음, 해당 없음, 확인 실패를 구분해야 한다.
- **DT-003**: 자동 추출 또는 유사 공고 제안은 확인 가능한 근거를 사용자에게 표시해야 한다.
- **DT-004**: 시스템은 로그인, 접근 제한 또는 기술적 차단을 우회해 정보를 가져와서는 안 된다.
- **DT-005**: 원문을 확인할 수 없는 경우 시스템은 실패 이유와 마지막 성공 시각을 표시하고 원문 이동 및 수동 입력 경로를 제공해야 한다.
- **DT-006**: 상세 화면 진입으로 시작된 최신 상태 확인이 실패해도 마지막으로 저장된 값과 그 출처 상태를 유지해야 한다.
- **DT-007**: 저장된 공고 정보가 원문을 대체하지 않으며 최종 확인은 원문에서 해야 함을 사용자에게 표시해야 한다.
- **DT-008**: 짧은 요약은 원문에서 확인한 내용과 정규화·추론한 표현을 구분하고 원문 전체의 보존본처럼 표시해서는 안 된다.

### User Control & Recovery Requirements *(mandatory when user data is involved)*

- **UR-001**: 시스템은 사용자 확인 없이 공고를 자동 병합하거나 사용자 작성 값을 덮어써서는 안 된다.
- **UR-002**: 사용자는 시스템이 추출·정규화·추론한 값을 수정할 수 있어야 한다.
- **UR-003**: 사용자는 중복 확정과 분리를 되돌릴 수 있어야 한다.
- **UR-004**: 외부 원문 상태 변화는 사용자 메모, 일정, 지원 상태를 삭제해서는 안 된다.
- **UR-005**: 내보내기와 복원은 공고, 출처, 중복 판단, 상태 이력, 메모, 일정을 포함해야 한다.
- **UR-006**: 복원은 검증이 완료되기 전에 기존 사용자 데이터를 비가역적으로 변경해서는 안 된다.
- **UR-007**: 시스템은 서로 다른 Google 계정의 공고와 지원 기록을 분리하고 다른 사용자에게 노출해서는 안 된다.
- **UR-008**: 동기화 충돌 처리는 사용자 작성 값을 비가역적으로 삭제해서는 안 되며 이전 값 복구 수단을 제공해야 한다.

### Key Entities *(include if feature involves data)*

- **사용자 계정**: Google SSO로 확인된 개인 사용자의 식별자와 개인 데이터 소유 관계를 나타낸다. 서로 다른 계정의 데이터는 분리된다.

- **채용공고**: 회사, 직무, 근무조건, 요구조건, 게시·마감 정보, 짧은 요약 및 사용자 판단의 기준이 되는 표준화된 모집 단위다. 원문 전체 본문은 포함하지 않는다.
- **공고 출처**: 플랫폼 또는 기업 페이지의 이름, 원문 URL, 게시 상태와 확인 시각이다. 하나의 채용공고가 여러 출처를 가질 수 있다.
- **공고 값의 출처 상태**: 각 값이 원문 확인, 정규화·추론, 사용자 입력, 정보 없음, 해당 없음, 확인 실패 중 어디에 해당하는지 나타낸다.
- **중복 그룹**: 사용자가 동일한 채용 기회라고 확정한 여러 공고 또는 출처의 묶음이다. 자동 제안은 가능하지만 최종 판단은 사용자가 한다.
- **지원 활동**: 현재 지원 상태, 상태 변경 이력, 개인 메모 및 다음 행동 일정이다.
- **변경 이력**: 동기화 충돌을 포함한 값 변경 전후 내용, 변경 시각과 변경 기기를 기록하며 사용자가 이전 값으로 복구하는 근거가 된다.
- **원문 확인 기록**: 원문 접근 성공 여부, 실패 이유, 확인 시각 및 마지막 성공 시각이다.
- **데이터 내보내기 묶음**: 사용자가 소유한 공고와 지원 기록을 다른 저장 상태로 옮기거나 복원하기 위한 전체 데이터 단위다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 발견한 공고 하나를 2분 이내에 등록하고 통합 목록에서 확인할 수 있다.
- **SC-002**: 100개 이상의 저장된 공고에서 원하는 조건의 후보를 30초 이내에 찾을 수 있다.
- **SC-003**: 승인된 사람인·잡코리아 공식 API 응답으로 만든 비식별 fixture 시험 세트에서 회사명, 제목, 출처, 원문 URL의 90% 이상이 정확히 표시된다. 승인된 fixture가 없는 제공자는 커넥터를 활성화하지 않고 이 기준을 적용하지 않는다.
- **SC-004**: 동일 URL의 중복 저장은 시험 사례의 100%에서 사전에 안내된다.
- **SC-005**: 명백히 동일한 시험 공고의 80% 이상이 중복 후보로 제시되며 서로 다른 공고는 사용자 확인 없이 병합되지 않는다.
- **SC-006**: 사용자는 3번 이하의 주요 조작으로 공고의 관심 또는 지원 상태를 변경할 수 있다.
- **SC-007**: 마감일이 알려진 시험 공고의 100%가 현재 날짜에 맞는 임박·마감 상태로 분류된다.
- **SC-008**: 원문 확인 실패나 일부 정보 누락이 있어도 사용자는 수동 입력으로 공고 등록을 완료할 수 있다.
- **SC-009**: 내보내기 후 복원 시험에서 사용자 작성 정보와 상태 이력의 100%가 유지된다.
- **SC-010**: 사용자가 일주일간 실제 구직 활동에 사용한 뒤 여러 사이트의 공고를 다시 찾고 상태를 기억하는 부담이 줄었다고 평가한다.
- **SC-011**: 사용자는 Google 계정으로 1분 이내에 로그인하고, 한 기기에서 저장한 변경사항을 동일 계정의 다른 기기에서 10초 이내에 확인할 수 있다.
- **SC-012**: 두 기기에서 같은 값을 충돌하게 수정하는 시험에서 가장 최근 값이 현재값이 되고 이전 값의 100%가 변경 이력에서 복구 가능하다.
- **SC-013**: 사람인·잡코리아 공고 상세 화면은 저장된 내용을 2초 이내에 표시하고, 시험 공고의 95%에서 최신 상태 확인 결과를 10초 이내에 추가로 보여준다.

## Assumptions

- 각 Google 계정은 본인의 취업 또는 이직 활동만 관리하는 독립적인 개인 사용자다.
- 여러 기기에서 동기화된 데이터에 접근하려면 Google 계정과 인터넷 연결이 필요하다.
- MVP의 기본 유입 경로는 사용자가 직접 발견한 공고 URL 등록이다.
- 사람인·잡코리아는 사전 승인과 서버 자격 증명이 확인된 공식 API의 허용된 구조화 정보만 MVP 자동 조회 대상으로 삼는다.
- 잡플래닛과 그 밖의 출처는 MVP에서 URL 보관과 수동 입력으로 지원한다.
- 자동 확인이 불가능한 정보는 추정하지 않고 사용자가 직접 입력할 수 있게 한다.
- 중복 판정 오류의 비용이 크므로 자동 병합보다 사용자 확인을 우선한다.
- 원문이 사라져도 저장된 구조화 항목, 짧은 요약과 사용자가 작성한 지원 기록은 보존하지만 전체 원문 본문은 보존하지 않는다.
- 공개 서비스 전환은 계정, 개인정보, 삭제 정책, 운영 정책 및 출처별 이용 조건을 포함하는 별도 기능으로 정의한다.

## Dependencies & Constraints

- 사람인·잡코리아의 공식 API 승인, 제공 필드, 호출 제한과 이용 조건이 MVP 자동 조회 범위를 제한하며 승인 전에는 수동 등록만 제공한다.
- 잡플래닛과 그 밖의 출처는 자동 추출을 제공하지 않아도 URL과 사용자 입력값을 보존해야 한다.
- 출처에서 제공하지 않거나 명확하지 않은 정보의 정확성을 시스템이 임의로 보완할 수 없다.
- 공고 내용과 모집 상태의 최종 기준은 해당 출처의 원문이다.
- 개인 메모와 지원 이력은 해당 Google 계정 사용자만 접근할 수 있어야 하며 채용 사이트 인증 정보를 저장하지 않는다.
- 로그인과 기기 간 동기화는 Google SSO의 이용 가능성과 네트워크 연결에 의존한다.
- MVP는 구조화 정보와 짧은 요약만 제공하며 원문 전체를 대체하여 재게시하는 서비스가 아니다.
