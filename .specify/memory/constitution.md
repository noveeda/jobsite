# 통합 채용공고 허브 Constitution

## Core Principles

### I. 개인 사용 가치 우선

모든 기능은 개인 사용자가 채용공고를 발견하고, 비교하고, 판단하고, 지원 상태를
관리하는 구체적인 문제에서 출발해야 한다. 각 기능 명세는 독립적으로 검증 가능한
사용자 시나리오와 측정 가능한 성공 기준을 반드시 포함해야 한다. 공개 서비스,
다중 사용자, 자동화 확대는 현재 개인용 흐름이 검증된 뒤 별도 명세로 다룬다.

기능이 핵심 사용자 흐름을 직접 개선한다는 근거가 없으면 MVP에 포함하지 않는다.
이 원칙은 바이브 코딩 중 아이디어가 늘어나 제품의 중심을 잃는 일을 방지한다.

### II. 출처 준수와 추적성

외부 채용정보를 다루는 모든 기능은 출처 이름, 원문 URL, 정보 확인 시각을 반드시
보존해야 한다. 원문이 최종 기준임을 사용자에게 명확히 보여주고, 저장된 정보가
원문을 대체한다고 표현해서는 안 된다. 접근 제한, 로그인, 기술적 차단 또는 출처의
이용 조건을 우회하는 수집 방식은 사용해서는 안 된다.

새로운 출처 연동은 구현 전에 허용된 접근 방식, 저장 범위, 표시 방식, 실패 시
동작을 문서화해야 한다. 출처를 확인할 수 없는 데이터는 일반 채용공고와 동일한
신뢰 수준으로 표시해서는 안 된다.

### III. 사실·추정·사용자 입력의 분리

제품은 원문에서 확인한 사실, 시스템이 정규화하거나 추론한 값, 사용자가 직접
입력한 값을 구분해 보존하고 표시해야 한다. 확인되지 않은 값을 사실처럼 채우거나
누락된 조건을 임의로 생성해서는 안 된다. 자동 추출이나 중복 판정에 확신이 없으면
불확실성과 판단 근거를 보여주고 사용자가 수정할 수 있어야 한다.

정보 수집 실패는 숨기지 않고 원인과 마지막 성공 시각을 표시해야 하며, 핵심 흐름은
수동 입력 또는 원문 확인 경로로 계속 진행할 수 있어야 한다. 정확성은 자동화율보다
우선한다.

### IV. 사용자 통제와 복구 가능성

자동화는 사용자가 작성한 메모, 지원 상태, 일정 또는 중복 판단을 사용자 확인 없이
삭제하거나 비가역적으로 덮어써서는 안 된다. 자동 중복 처리는 후보 제안까지만
허용하며, 병합·분리·수정의 최종 결정과 되돌리기 수단을 사용자에게 제공해야 한다.

사용자가 만든 모든 핵심 데이터는 내보내기와 복원이 가능해야 한다. 원문이 사라지거나
연동이 실패해도 개인의 지원 활동 기록은 유지되어야 한다. 파괴적 데이터 변경은 명시적
확인과 검증 가능한 복구 경로가 있을 때만 허용한다.

### V. 단순하고 독립 검증 가능한 개발

각 변경은 가장 작은 가치 단위로 구현하고 독립적으로 시연·검증할 수 있어야 한다.
현재 명세에 필요하지 않은 추상화, 서비스 분리, 의존성, 확장 지점을 미리 추가해서는
안 된다. 복잡한 설계나 새 의존성은 더 단순한 방법이 요구사항을 충족하지 못하는
구체적인 이유를 계획에 기록해야 한다.

공고 등록, 추출 실패 복구, 중복 판단, 지원 상태 보존, 데이터 내보내기·복원처럼
데이터 손실이나 잘못된 판단으로 이어질 수 있는 흐름은 자동화된 검증을 반드시 가진다.
그 밖의 검증 범위는 위험도에 비례한다. 변경은 해당 사용자 시나리오의 인수 조건을
통과하기 전 완료로 간주하지 않는다.

## 데이터 및 개인정보 제약

- 개인용 단계의 저장 데이터는 기본적으로 사용자 본인만 접근할 수 있어야 한다.
- 외부 사이트 계정의 비밀번호, 세션 값 또는 인증 정보를 프로젝트 파일이나 사용자
  데이터로 수집·보관해서는 안 된다.
- 개인 메모와 지원 이력은 제품 기능에 필요한 최소 범위로만 처리한다.
- `정보 없음`, `해당 없음`, `확인 실패`, `사용자 입력`은 서로 구분되어야 한다.
- 외부 공개 배포 전에 계정, 접근 제어, 개인정보 처리, 데이터 삭제, 운영 정책 및
  출처별 이용 조건을 별도 명세와 검증 대상으로 추가해야 한다.
- 실제 입사지원 제출, 기업 리뷰·연봉 정보 재배포, 접근 제한 우회는 별도 승인과
  정당한 데이터 사용 근거 없이 범위에 포함할 수 없다.

## 개발 흐름과 품질 게이트

1. Constitution은 기능 명세, 구현 계획, 작업 목록보다 먼저 적용한다.
2. 기능 명세는 포함·제외 범위, 독립 사용자 시나리오, 출처·데이터 신뢰 요구사항,
   실패·복구 경로, 측정 가능한 성공 기준을 반드시 포함한다.
3. 구현 계획은 외부 출처 사용 방식, 데이터 소유권과 복구, 불확실성 표시, 단순성
   선택을 Constitution Check에서 검증한다.
4. 작업 목록은 위험한 핵심 흐름의 검증 작업을 구현보다 앞에 배치하고, 각 작업을
   요구사항 또는 사용자 시나리오에 연결한다.
5. 구현 전 계획 단계와 설계 후 단계에서 Constitution Check를 각각 수행한다.
6. 완료 보고에는 실행한 검증, 통과 결과, 남은 제약과 수동 확인 항목을 기록한다.
7. Constitution 위반이 필요한 경우 구현을 진행하지 않고 위반 사유와 더 단순하거나
   안전한 대안을 먼저 제시한다.

## Governance

이 Constitution은 프로젝트 안의 다른 관행과 문서보다 우선한다. 기능 명세, 계획,
작업, 구현이 MUST 규칙과 충돌하면 하위 산출물을 수정해야 하며 원칙을 암묵적으로
완화해서는 안 된다.

개정은 변경 이유, 영향받는 원칙과 템플릿, 기존 작업의 이행 방법을 문서화한 뒤
승인한다. 버전은 의미론적 버전 규칙을 따른다.

- **MAJOR**: 원칙 제거, 의미 반전 또는 기존 보호 장치의 비호환 완화
- **MINOR**: 새 원칙·필수 게이트 추가 또는 기존 원칙의 실질적 확대
- **PATCH**: 의미를 바꾸지 않는 명확화, 표현 개선 또는 오탈자 수정

모든 기능 계획과 작업 검토는 Constitution 준수 여부를 확인해야 한다. 복잡성 예외는
계획의 Complexity Tracking에 이유와 기각한 단순 대안을 기록해야 한다. 준수 여부를
판정할 수 없으면 구현 전에 명세 또는 계획을 보완한다.
